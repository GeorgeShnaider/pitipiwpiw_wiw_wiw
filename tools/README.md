# tools — эмулятор буя для отладки WebApp

`mock_buoy.py` заменяет буй на ПК: отдаёт `data/index.html` и на **том же порту** обслуживает WebSocket `/ws`.
Так WebApp работает без изменений: он подключается к `ws://<location.host>/ws`.

| Путь | Что делает |
|---|---|
| `GET /`, `GET /index.html` | отдаёт `data/index.html`, файл перечитывается при каждом запросе (правка и F5) |
| `WS /ws` ← text | команды WebApp (контракт №1): проверка формата и частоты |
| `WS /ws` → text | телеметрия 10 Гц (контракт №3, протокол v2), значения плавно меняются, `vbat` проходит 16.6 → 12.8 В за 45 с, чтобы были видны все цвета; `armed` — фактическое состояние «ТНПА»: повторяет `armed` последней cmd с задержкой 100 мс, 0 при паузе cmd > 300 мс |
| `WS /ws` → binary | JPEG-кадры 320×240 (контракт №4, только JPEG-байты), по умолчанию 10 к/с |

Знаки телеметрии как в ICD §6: `roll` + — правый борт вниз, `pitch` + — нос вверх, `yaw` растёт при повороте вправо. В mock курс равномерно растёт (аппарат «крутится» вправо), крен и дифферент качаются по синусу.

## Установка

Нужен Python 3.9+ и пакет `websockets` версии 13 или новее. Pillow не обязателен.

```bash
python3 -m venv .venv            # папка .venv не коммитится
.venv/bin/pip install "websockets>=13"
.venv/bin/pip install pillow     # необязательно: кадры с текстом
```

Без Pillow кадры строит встроенный минимальный JPEG-кодер (`tools/jpeg_mini.py`, общий с `bench_link.py`): мозаика из блоков 8×8 с бегущей жёлтой полосой, перекрестием и номером кадра.

## Запуск

```bash
.venv/bin/python tools/mock_buoy.py                 # 0.0.0.0:8080
.venv/bin/python tools/mock_buoy.py --drop          # каждые 10 с молчит 3 с
.venv/bin/python tools/mock_buoy.py --frames ~/jpg  # свои JPEG по кругу (≤ 32768 байт)
```

| Флаг | По умолчанию | Назначение |
|---|---|---|
| `--host` | `0.0.0.0` | адрес прослушивания (0.0.0.0, чтобы зайти с телефона) |
| `--port` | `8080` | порт HTTP и WS |
| `--fps` | `10` | частота видеокадров; `0` — видео не шлётся (буй без камеры, видна заглушка «нет видео») |
| `--frames DIR` | — | папка с `*.jpg`/`*.jpeg` вместо генератора |
| `--no-vbat` | выкл. | слать `vbat` 0.00: напряжение не измеряется (ICD §6, D-009), WebApp показывает «АКБ —» серым |
| `--no-pil` | — | использовать встроенный кодер, даже если Pillow установлен |
| `--drop` | выкл. | периодически не слать ни телеметрию, ни видео (проверка «НЕТ СВЯЗИ») |
| `--drop-period`, `--drop-len` | `10`, `3` | цикл и длительность молчания, с |
| `--rov-disarm-after N` | `0` (выкл.) | через N с после взвода «ТНПА» сообщает `armed:0`, хотя cmd идут с `armed=1` (имитация обрыва линии команд вниз, D-010) |
| `--no-armed` | выкл. | телеметрия протокола v1 без ключа `armed` (старая прошивка rov_core) |
| `--duration N` | `0` | завершиться через N с (для автотестов), 0 — работать до Ctrl+C |
| `-v` | выкл. | печатать каждую принятую команду |

## Открыть WebApp с телефона

1. Телефон и ПК должны быть в **одной** Wi-Fi сети. Гостевые сети и сети с «изоляцией клиентов» не подходят. Можно раздать точку доступа с телефона и подключить к ней ПК.
2. Запустите mock. Он напечатает адреса вида `с телефона: http://192.168.1.23:8080/`.
3. Откройте этот адрес в Chrome (Android) или Safari (iOS). Поверните телефон горизонтально и нажмите «⛶ Экран».
   - На iPhone Safari не даёт полноэкранный режим страницам. Вместо этого: «Поделиться» → «На экран Домой» и открывать с иконки.
4. Если страница не открывается, проверьте брандмауэр ПК: входящие соединения на порт 8080 для Python должны быть разрешены. На macOS при первом запуске появится запрос, его нужно разрешить.

## Что печатает mock

Раз в секунду для каждого клиента:

```
[cmd] 20 Гц OK   ошибок 0 | dt  45.. 55 мс | armed=1 light=0 | surge=+0.81 yaw=+0.28 heave=-0.81 sway=-0.28
```

- `20 Гц OK` — за секунду пришло 20 ± 1 команд, иначе `WARN`.
- `dt` — минимальный и максимальный интервал между командами. Пауза больше 300 мс (`BUOY_WS_TIMEOUT_MS`) отдельно печатается как WARN: настоящий буй в этот момент ушёл бы в fail-safe.
- Смена `armed`/`light` печатается отдельной строкой.
- Смена фактического armed «ТНПА» в телеметрии печатается как `[rov] armed ТНПА: 0 -> 1`.
- Каждая команда проверяется строго по контракту №1: лишние или отсутствующие ключи (в корне и в `axes`), порядок ключей, `type == "cmd"`, `armed`/`light` типа bool, оси — числа в диапазоне −1..+1. При нарушении печатается `[cmd] WARN: <причины> | <сообщение>`.

## Ручная проверка WebApp по mock

- Оба джойстика двигаются одновременно, в строке mock видно знаки: левый вверх — `surge` +, вправо — `yaw` +; правый вверх — `heave` +, вправо — `sway` +. Отпускание возвращает оси в 0.
- ARM взводится только удержанием 1 с, DISARM срабатывает от одного касания.
- Сворачивание вкладки или блокировка экрана приводят к `armed: True -> False` в логе mock.
- Остановка mock (Ctrl+C): WebApp показывает «НЕТ СВЯЗИ» и «Снято с охраны: WS закрыт». После повторного запуска он сам переподключается в течение 1 с, уже с `armed=0`.
- С флагом `--drop` индикатор переходит в «НЕТ СВЯЗИ» примерно через 1 с после начала молчания и возвращается, когда телеметрия снова идёт. По ICD §8, если WebApp был взведён, в каждом цикле молчания в логе mock появляется `armed: True -> False`, оси обнуляются, джойстики отпускаются. Пока телеметрии нет, кнопка ARM неактивна и удержание не взводит. После восстановления WebApp **сам не взводится**, нужно снова удержать ARM.
- Плашка над кнопками показывает фактическое состояние ТНПА из телеметрии: «ТНПА: НЕ ВЗВЕДЁН», «ТНПА: ВЗВЕДЁН» (красная) или «ТНПА: —», если телеметрии нет или прошивка старая (без ключа `armed`). После ARM плашка становится красной через ~0.1 с.
- `--rov-disarm-after 5`: через 5 с после ARM плашка становится жёлтой «ТНПА: НЕ ВЗВЕДЁН». Ещё через ~1 с WebApp снимает взвод с сообщением «Снято с охраны: ТНПА не получает команды» (ICD §8, D-010), оси обнуляются. Сам WebApp не взводится, взвести снова можно только удержанием ARM.
- `--no-armed`: строки без `armed` принимаются как раньше (глубина и углы обновляются), плашка показывает «ТНПА: —», взвод работает.

# cam_rx.py — приёмка камеры без буя

`cam_rx.py` принимает видеопоток ESP32-CAM по контракту №4 (ICD §7) с USB-UART или разбирает записанный файл. Он проверяет магию, XOR заголовка, длину (1..32768) и CRC16-CCITT, сохраняет целые кадры в `.jpg` и считает статистику: к/с, КиБ/с, битые CRC, плохие заголовки, пропуски `seq`, не-JPEG, байты мусора.

## Подключение

- ESP32-CAM, **GPIO13** (`CAM_VIDEO_TX_PIN`, UART1 TX) → **RX** USB-UART адаптера, **GND ↔ GND**. TX адаптера никуда не подключается: камера только передаёт.
- Адаптер должен быть на **3.3 В** и держать **921600** бод (`VIDEO_BAUD`): CP2102 или CH340 подходят, PL2303 старых ревизий нет.
- Если на линии уже стоит трансивер RS-485, вместо USB-UART используйте USB-RS485 адаптер на пару 4 (A↔A, B↔B).
- Питание ESP32-CAM: 5 В от отдельного источника или адаптера, не меньше 500 мА.

## Установка и запуск

```bash
.venv/bin/pip install pyserial                       # нужен только для --port
.venv/bin/python tools/cam_rx.py --port /dev/tty.usbserial-0001 --out frames       # macOS/Linux
.venv/bin/python tools/cam_rx.py --port COM5 --dump raw.bin --duration 30           # Windows, с записью сырого потока
.venv/bin/python tools/cam_rx.py --file raw.bin --out frames                        # разбор записи, pyserial не нужен
```

| Флаг | По умолчанию | Назначение |
|---|---|---|
| `--port` / `--file` | — (одно обязательно) | источник: последовательный порт или файл |
| `--baud` | `921600` | скорость порта |
| `--out` | `frames` | каталог для `frame_<n>_seq<seq>.jpg` |
| `--no-save` | — | только статистика, без записи кадров |
| `--dump FILE` | — | дописывать сырой поток в файл (режим `--port`) |
| `--duration N` | `0` | секунд приёма, 0 — до Ctrl+C |
| `--chunk` | `4096` | размер порции чтения из файла |

В режиме `--port` раз в секунду печатается строка `[порт] … к/с, … КиБ/с | целых …, битых CRC … (…%) …`, в конце печатается ИТОГ, размеры кадров и средняя частота. Приёмка: частота около `CAM_TARGET_FPS`, битых CRC меньше 1 %, кадры в `frames/` открываются как картинки.

# bench_link.py — стенд (этап 7)

`bench_link.py` подменяет соседний узел, чтобы каждую плату можно было проверить отдельно через USB-UART адаптер (CP2102/CH340). Нужна только библиотека `pyserial`. Подробная справка: `python3 tools/bench_link.py <режим> --help`, там же схема проводов.

```bash
.venv/bin/pip install pyserial
.venv/bin/python tools/bench_link.py --help
```

**Перед подключением:**
- Адаптер **строго 3.3 В по сигналам**: перемычка 3V3, не 5V. 5 В на GPIO выводит ESP32 из строя.
- **Общая земля обязательна**: GND адаптера соединяется с GND платы.
- **RX↔TX крест-накрест**: TX адаптера идёт на RX платы, RX адаптера — на TX платы.
- Подключаться нужно к GPIO самой ESP32. Если трансивер RS-485 (MAX3490/MAX3485) уже припаян, его выход RO конфликтует с TX адаптера на том же GPIO. В этом случае трансивер отключают от пина или используют USB-RS485 адаптер на пары кабеля (A↔A, B↔B).
- Лог платы читается по её собственному USB: `pio device monitor -e <env>`. Порт адаптера и порт платы — разные устройства.
- Для сценариев с `armed=1` у `rov_core` **винты сняты**.

Константы протокола (заголовки, частоты, таймауты, пины для подсказок) собраны в начале `bench_link.py` со ссылками на `protocol.h`/`config.h`. Если там что-то изменится, константы нужно поправить и здесь.

## emulate-buoy — ПК вместо буя, проверка ROV_CORE

Провода: **TX адаптера → GPIO16** rov_core (`ROV_LINK_RX_PIN`), **RX адаптера ← GPIO17** (`ROV_LINK_TX_PIN`), GND–GND. Скорость 115200.

```bash
.venv/bin/python tools/bench_link.py emulate-buoy --port /dev/tty.usbserial-0001 --scenario idle
```

Утилита шлёт ControlPacket (контракт №2) ровно 20 Гц и проверяет каждую строку телеметрии (контракт №3): `\n` в конце, длина ≤ 160 Б, JSON, ровно 7 ключей в порядке `depth,temp,vbat,roll,pitch,yaw,armed` (протокол v2), числа, `armed` — 0 или 1, формат `TELEMETRY_JSON_FMT`. Строка без `armed` считается битой с причиной «прошивка rov_core протокола v1». Раз в секунду печатается строка: `вниз 20.0 пак/с | телем 10.0 Гц (10 за 1.00 с) OK, целых …, битых 0 | <фаза> | ТНПА armed=1 | depth=… vbat=— (не измеряется) …`. Смена фактического armed ТНПА печатается отдельно: `[телем] armed ТНПА 1 -> 0 (время)`; в `failsafe` она приходит через ~0.5 с после начала тишины. Каждая битая строка печатается отдельно как `[телем] БИТАЯ строка: <причина>: <начало строки>`. В начале каждой фазы сценария выводится `ФАЗА k/n` и строка «ожидание в логе rov_core: …» — её сверяют с логом платы.

| Сценарий | Что шлёт | Что должно быть в логе rov_core |
|---|---|---|
| `idle` | armed=0, оси 0, до Ctrl+C | `пакетов/с=20`, ошибок 0, `armed=0`, причина «команда armed=0», M0..M3=1500 |
| `arm-sweep` | 3.5 с armed=0, затем armed=1 и по очереди surge, yaw, heave, sway: +0.5 2 с, −0.5 2 с, 0 1 с; в конце armed=0 1 с | `[rov_core] ARMED`; при +0.5 surge M0=M1=1600, yaw M0=1600/M1=1400, heave M2=1600, sway M3=1600 (1500 + 400·u при ESC 1100/1500/1900, THRUST_LIMIT 0.5, нарастание с slew; точные числа печатаются в подсказке фазы); в конце `DISARM: команда armed=0`. Знаки и направление винтов сверяются по ICD §9 |
| `failsafe` | 3.5 с armed=0, armed=1 surge=0.3 3 с, **2 с тишины**, снова armed=1 surge=0.3 3 с, armed=0 1 с | ARMED; через 500 мс тишины `DISARM: нет связи`, M=1500, `пакетов/с=0`; после возобновления снова `ARMED` (таймаут сбросил детектор фронта); затем `DISARM: команда armed=0` |
| `edge` | ждёт сброса платы (см. ниже), затем armed=1 5 с, armed=0 1 с, armed=1 3 с, armed=0 1 с | первые 5 с `ARMED` **нет**, причина «ждём фронт armed 0->1»; после armed=0→1 — `ARMED`; затем `DISARM: команда armed=0` |
| `badcrc` | 3.5 с armed=0, armed=1 1 с, 6 с смеси (50 % битый CRC, 25 % ось=101, 25 % валидные), armed=1 1 с, armed=0 1 с | `пакетов/с≈5`, «ошибок CRC» растёт на ≈10/с, «вне диапазона» на ≈5/с, `armed=1` держится, `DISARM` в этой фазе нет |
| `light` | armed=0, light переключается каждые 2 с, до Ctrl+C | `свет=` чередуется 0/1, LED-лента на GPIO4 мигает, M=1500 |

**Сброс платы для `edge`.** Окно старта `ESC_ARM_TIME_MS` отсчитывается от сброса rov_core. Поэтому у `edge` по умолчанию включён `--wait-boot`: утилита ничего не шлёт и ждёт, пока после паузы телеметрии ≥ 0.4 с не появится новая строка. Порядок такой: запустить утилиту, затем нажать EN на rov_core. Для других сценариев режим включается флагом `--wait-boot`. Сценарии `arm-sweep`, `failsafe` и `badcrc` начинаются с 3.5 с armed=0, поэтому работают и сразу после сброса, и на давно работающей плате.

Ключи: `--duration N` — остановиться через N с; `-v` — печатать каждый пакет в hex; `--no-wait-boot` — не ждать сброса. По Ctrl+C или в конце сценария утилита шлёт 3 пакета armed=0 и печатает ИТОГ. Код выхода 1, если была битая телеметрия.

**Прошло:** телеметрия `10.0 Гц … OK`, битых строк 0; лог rov_core во всех фазах совпадает со строками «ожидание»; в `failsafe` DISARM приходит примерно через 0.5 с после начала тишины.

## emulate-rov — ПК вместо ТНПА, проверка буя

Провода: **RX адаптера ← GPIO17** буя (`BUOY_LINK_TX_PIN`), **TX адаптера → GPIO16** буя (`BUOY_LINK_RX_PIN`), GND–GND. Скорость 115200.

```bash
.venv/bin/python tools/bench_link.py emulate-rov --port /dev/tty.usbserial-0001 --no-vbat
```

Утилита ищет ControlPacket скользящим окном (повторяет `packet_parser.cpp` rov_core) и проверяет CRC и диапазон ±100. Одновременно она шлёт вверх синтетическую телеметрию 10 Гц (как `mock_buoy.py`; с `--no-vbat` — vbat=0). Ключ `armed` равен флагу последнего валидного пакета или 0, если пакетов нет дольше 500 мс (как у ROV_CORE, но без окна старта и правила фронта). Раз в секунду печатается:

```
пакеты 20.0 Гц (20 за 1.00 с) OK | dt  46.. 54 мс OK | битых CRC 0, вне диап. 0, мусор 0 Б | armed=0 light=0 surge=  +0 … | телем вверх 10.0/с
```

Частота считается по среднему интервалу внутри секунды, поэтому не прыгает на ±1 из-за того, где легла граница окна. Отдельными строками с меткой времени печатаются:
- `ПЕРЕХОД armed 1 -> 0 (время чч:мм:сс.мс, предыдущий пакет N мс назад)` и смена света;
- `НЕТ ПАКЕТОВ уже 500 мс` — в этот момент rov_core ушёл бы в fail-safe;
- `СВЯЗЬ ВЕРНУЛАСЬ после паузы N мс`.

`--csv FILE` пишет каждый валидный пакет (время, hex, поля) для разбора после теста, `-v` печатает каждый пакет.

Что проверять с телефоном (WebApp открыт с буя):
- без клиента буй всё равно шлёт пакеты 20 Гц с `armed=0` (ICD §5);
- джойстики меняют `surge/yaw/heave/sway` с правильными знаками, ARM удержанием даёт `ПЕРЕХОД armed 0 -> 1`;
- закрыли вкладку или свернули браузер → `ПЕРЕХОД armed 1 -> 0` сразу, в пределах 1–2 пакетов;
- телефон отключили от Wi-Fi (авиарежим) → `armed 1 -> 0` не позже 300 мс (`BUOY_WS_TIMEOUT_MS`) после последней cmd. Время отключения можно отметить по логу буя («клиент отключён») или по секундомеру;
- в WebApp видна синтетическая телеметрия, плашка «ТНПА: ВЗВЕДЁН» следует за ARM/DISARM.

**Прошло:** `пакеты 20 ± 1 Гц OK`, `dt` максимум ≤ 60 мс, битых CRC и вне диапазона 0, строк `НЕТ ПАКЕТОВ` нет за всё время работы (без клиента тоже), переходы armed соответствуют действиям на телефоне.

## send-video — ПК вместо камеры, проверка видеовхода буя

Провода: **TX адаптера → GPIO18** буя (`BUOY_VIDEO_RX_PIN`, UART1 RX), GND–GND. RX адаптера не нужен. Скорость 921600: адаптер должен её держать (CP2102/CH340 подходят).

```bash
.venv/bin/python tools/bench_link.py send-video --port /dev/tty.usbserial-0001 --fps 10
.venv/bin/python tools/bench_link.py send-video --port /dev/tty.usbserial-0001 --fps 10 --corrupt 10
.venv/bin/python tools/bench_link.py send-video --port /dev/tty.usbserial-0001 --file test/test_buoy/fixtures/cam_stream.bin --loop
```

Без `--file` шлются кадры контракта №4: заголовок 10 Б с XOR, JPEG 320×240 из `jpeg_mini.py` (около 3 КБ) и CRC16-CCITT. Частота задаётся `--fps` (по умолчанию `CAM_TARGET_FPS` = 10). `--corrupt N` портит CRC каждого N-го кадра, `--count N` — выход после N кадров. С `--file` файл шлётся как есть, порциями по 1 КБ, со скоростью линии (baud/10 Б/с) или `--bps`; `--loop` повторяет файл. Раз в секунду печатается `отправлено 10.0 к/с, 29.4 КиБ/с | всего кадров …`.

В логе буя раз в 5 с появляется `[buoy] видео: ок N (10.00 к/с), битых заголовков 0, битых CRC 0, мусор 0 Б | в WS …`. Если WebApp открыт, в нём идёт тестовая мозаика с бегущей полосой и номером кадра.

**Прошло:** у буя «ок» ≈ `--fps`, битых 0; с `--corrupt 10` «битых CRC» ≈ 1/10 от отправленных, остальные кадры целые. С `cam_stream.bin` за один проход: 10 целых, 2 битых CRC, 4 плохих заголовка (как в `cam_stream.expected` — это ожидание хост-теста парсера буя).

## Самопроверка без железа

Две утилиты можно соединить через пару виртуальных портов (на Linux — `socat -d -d pty,raw,echo=0 pty,raw,echo=0`): `emulate-buoy` на одном конце, `emulate-rov` на другом. Каждая видит данные другой с нулём ошибок, 20 Гц вниз и 10 Гц вверх. `send-video` проверяется так же через `cam_rx.py --port`. На macOS pty не принимает нестандартную скорость 921600, поэтому для pty обоим ставят `--baud 115200`: виртуальный порт скорость игнорирует, на настоящем адаптере это ограничение не действует.
