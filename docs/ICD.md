# ICD — описание интерфейсов системы ТНПА

Документ ведёт **лид (чат 0)**. Код в `include/protocol.h` и `include/config.h` обязан совпадать с этим документом. При расхождении прав этот документ, а код исправляется.

Версия протокола: **1** (`PROTOCOL_VERSION`).

---

## 1. Узлы и контуры

```
 Телефон (браузер, WebApp)
     │  Wi-Fi 2.4 ГГц, AP "ROV_BUOY_AP", 192.168.4.1
     │  HTTP GET /        -> index.html (LittleFS)
     │  WebSocket /ws     -> text: cmd ↓ / телеметрия ↑ ; binary: JPEG ↑
 ┌───┴────────────────────────────┐
 │ БУЙ (узел 6), ESP-WROOM-32      │
 │  UART2 ↔ кабель пары 2/3        │
 │  UART1 ← кабель пара 4 (видео)  │
 └───┬────────────────────────────┘
     │  Кабель 8 жил (4 витые пары), 10 м, RS-485
 ┌───┴──────────────────────┐      ┌──────────────────────────┐
 │ ROV_CORE (отсек 4)        │      │ CAM (отсек 5)             │
 │ ESP-WROOM-32              │      │ ESP32-CAM, OV2640          │
 │ 4 ESC, I2C датчики, АЦП,  │      │ JPEG -> UART1 TX -> пара 4 │
 │ подсветка                 │      │ (с rov_core не связана)    │
 └──────────────────────────┘      └──────────────────────────┘
```

| Контур | Путь | Частота |
|---|---|---|
| Управление | Телефон → WS text (№1) → Буй → UART пара 2 (№2) → ROV_CORE → ESC | 20 Гц |
| Телеметрия | Датчики → ROV_CORE → UART пара 3 (№3) → Буй → WS text (№3) → Телефон | 10 Гц |
| Видео | OV2640 → CAM → UART пара 4 (№4) → Буй → WS binary → Телефон | 5–15 к/с |

Видео не проходит через ROV_CORE.

## 2. Кабель (8 жил, 4 витые пары, нулевая плавучесть)

| Пара | Жилы | Сигнал | Направление | Скорость |
|---|---|---|---|---|
| 1 | +V / GND | Питание буя: VBAT 4S через предохранитель 1 А, понижающий DC-DC в буе | ТНПА → буй | — |
| 2 | A / B | RS-485: ControlPacket (контракт №2) | буй → ТНПА | 115200 8N1 |
| 3 | A / B | RS-485: телеметрия JSON (контракт №3) | ТНПА → буй | 115200 8N1 |
| 4 | A / B | RS-485: видео (контракт №4) | камера → буй | 921600 8N1 |

- Пары 2 и 3 на каждой стороне обслуживает один full-duplex трансивер **MAX3490/MAX3491** (3.3 В). Пару 4 обслуживает **MAX3485** с постоянным направлением: DE=1 на камере, DE=0/RE=0 на буе.
- Терминатор 120 Ом ставится на приёмном конце каждой пары.
- GND пары 1 служит общей опорой RS-485.

## 3. Пины (дубль `config.h`)

**ROV_CORE:** ESC `25, 26, 27, 13` (активные), `32, 33` (резерв); UART2 RX16/TX17; I2C SDA21/SCL22; VBAT ADC GPIO34; подсветка GPIO4; LED GPIO2.
**BUOY:** UART2 RX16 (телеметрия) / TX17 (управление); UART1 RX18 (видео); LED GPIO2.
**CAM:** UART1 TX GPIO13 (видео); вспышка GPIO4 всегда выключена.

## 4. Контракт №1 — WebApp → Буй (WebSocket text, 20 Гц)

```json
{"type":"cmd","armed":true,"light":false,"axes":{"surge":0.0,"yaw":0.0,"heave":0.0,"sway":0.0}}
```

- Оси: float от −1.0 до +1.0. Знаки: `surge` + вперёд, `yaw` + вправо, `heave` + вверх, `sway` + вправо.
- WebApp шлёт сообщение **каждые 50 мс**, даже если ничего не изменилось: это heartbeat.
- При сворачивании вкладки (`visibilitychange`) или закрытии сокета WebApp сбрасывает `armed=false` в UI.
- Буй игнорирует сообщения с другим `type` и с некорректным JSON; значения вне диапазона обрезает до ±1.0.

## 5. Контракт №2 — Буй → ТНПА (UART binary, 20 Гц)

`struct ControlPacket` (8 байт, packed):

| Байт | Поле | Тип | Значение |
|---|---|---|---|
| 0 | header1 | u8 | 0xAA |
| 1 | header2 | u8 | 0x55 |
| 2 | surge | i8 | −100..+100 |
| 3 | yaw | i8 | −100..+100 |
| 4 | heave | i8 | −100..+100 |
| 5 | sway | i8 | −100..+100 |
| 6 | flags | u8 | бит 0 armed, бит 1 light, остальные 0 |
| 7 | crc | u8 | XOR байт 0..6 |

- Перевод из float: `round(axis * 100)`, затем ограничение до ±100.
- Буй шлёт пакет **непрерывно с частотой 20 Гц** независимо от того, есть ли клиент.
- Приёмник ищет 0xAA 0x55 скользящим окном. Пакет с плохим CRC или осью вне диапазона отбрасывается целиком и fail-safe-таймер не сбрасывает.

## 6. Контракт №3 — ТНПА → Буй → WebApp (JSON-строка, 10 Гц)

```
{"depth":1.23,"temp":18.4,"vbat":15.62,"roll":-2.1,"pitch":0.8,"yaw":134.5}\n
```

| Ключ | Единицы | Примечание |
|---|---|---|
| depth | м | от поверхности, обнуляется по давлению при старте |
| temp | °C | с MS5837 |
| vbat | В | батарея 4S; **0 — не измеряется** (`VBAT_ENABLED 0`, делителя нет), WebApp показывает «—» |
| roll, pitch | градусы | ±180 / ±90 |
| yaw | градусы 0..360 | **относительный** курс (интеграл гироскопа, дрейфует), обнуляется при старте |

Знаки (уточнение, формат не меняется): `roll` + — правый борт вниз; `pitch` + — нос вверх; `yaw` растёт при повороте вправо (по часовой, если смотреть сверху), как ось `yaw` контракта №1.

- Формат `TELEMETRY_JSON_FMT`, максимум 160 байт с `\n`.
- Если датчик не отвечает, в поле передаётся последнее значение. Строка всегда содержит все 6 ключей.
- Буй пересылает строку в WebSocket **без изменений** (без `\n`) всем клиентам.

## 7. Контракт №4 — Камера → Буй → WebApp (видео)

**По кабелю** каждый кадр передаётся так:

```
[VideoFrameHeader 10 Б][JPEG length Б][CRC16-CCITT(JPEG) 2 Б, little-endian]
```

| Байт | Поле | Тип | Значение |
|---|---|---|---|
| 0 | magic1 | u8 | 0xA5 |
| 1 | magic2 | u8 | 0x5A |
| 2..3 | seq | u16 | счётчик кадров |
| 4..7 | length | u32 | 1..32768 |
| 8 | flags | u8 | 0 |
| 9 | hcrc | u8 | XOR байт 0..8 |

- CRC16-CCITT: полином 0x1021, начальное значение 0xFFFF (`crc16Update`).
- Камера не начинает новый кадр, пока предыдущий не ушёл в UART целиком. Частота ограничена `CAM_TARGET_FPS`.
- Буй: при плохом заголовке или CRC кадр отбрасывается и начинается поиск магии заново.

**В WebSocket** буй шлёт одно **binary**-сообщение на кадр, содержащее только JPEG-байты. Если очередь клиента заполнена, кадр пропускается (видео никогда не задерживает телеметрию). WebApp показывает кадр через `Blob` → `URL.createObjectURL` → `<img>` и освобождает предыдущий URL.

## 8. Fail-safe (обязательно)

| Уровень | Условие | Действие |
|---|---|---|
| WebApp | WS закрыт / вкладка скрыта | UI сбрасывает armed, показывает «НЕТ СВЯЗИ» |
| WebApp | телеметрии нет > 1 с (WS открыт) | UI сбрасывает armed, «НЕТ СВЯЗИ»; ARM заблокирован, пока телеметрия не станет свежей |
| Буй | нет `cmd` > 300 мс | шлёт вниз `armed=0`, все оси 0, light сохраняется |
| ROV_CORE | нет валидного ControlPacket > 500 мс | armed=false, все 6 ESC = 1500 мкс |
| ROV_CORE | старт | 1500 мкс на все ESC ≥ 3 с, armed=false до первого пакета с armed=1 |
| ROV_CORE | armed=0 | все ESC 1500 мкс, оси игнорируются |

**Правила взвода на ROV_CORE (уточнение, этап 1):**
- Вход в armed только по фронту флага armed 0→1 в принятых пакетах.
- Пакеты с armed=1, пришедшие в окне старта `ESC_ARM_TIME_MS`, фронт «съедают»: если буй всё это время шлёт armed=1, после окна ТНПА сам **не** взведётся, оператор должен сделать DISARM → ARM.
- Таймаут связи (> `FAILSAFE_TIMEOUT_MS`) сбрасывает детектор фронта в 0: если связь вернулась сразу с armed=1, ТНПА взведётся, тяга нарастает с нуля через slew.
- Подсветка при fail-safe сохраняет последнее принятое значение.

## 9. Движители (текущая конфигурация)

| Индекс | Мотор | Место | Оси |
|---|---|---|---|
| 0 | M_STERN_LEFT | отсек 1 | surge + yaw |
| 1 | M_STERN_RIGHT | отсек 1 | surge − yaw |
| 2 | M_BOW_VERT | отсек 2 | heave |
| 3 | M_BOW_HORIZ | отсек 2 | sway |
| 4, 5 | резерв | — | всегда 1500 мкс |

Обработка: `MIX` → нормализация по максимуму → `MOTOR_DIR` → `THRUST_LIMIT` → slew-rate → мёртвая зона → `1500 + 500·u` мкс.
ESC должны быть прошиты в режим **BLHeli_S Bidirectional**.
